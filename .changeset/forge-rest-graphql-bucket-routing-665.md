Route a GitHub read between the REST and GraphQL buckets (part of #665). GitHub meters REST (`core`) and GraphQL separately, so `agent_harness_lab.sources.routing.choose` now picks, per logical read, the transport that can supply its complete field set and has headroom: a read only one API supports is never sent to the other, a cached refresh stays on REST conditional requests (a 304 costs no primary quota), a first or aggregate fetch uses one GraphQL query when its points are fewer than the REST requests it replaces, a preferred bucket at its reserve floor yields to the other, and when every supported bucket is blocked the read halts as blocked access with the earliest reset, unless the block ends within `max_wait` and the collection deadline, in which case routing leaves the wait to the limiter exactly as an unrouted read would (a review-thread read with `max_wait` set still waits out a short GraphQL block). The GitHub reader opts in with the new `routing: "auto"` limit (default `"rest"`, unchanged behavior): issue and pull conversation comments of every selected number are then read through aliased GraphQL pages and normalized by the same code as the REST listing, so records and digests are identical; a number whose comment author GraphQL cannot name as REST does (a deleted account) is read from REST and never defaulted. GraphQL spend is charged from the response's reported `rateLimit` cost (new `points` per bucket in the receipt) and the reserve floor must survive a request's declared cost. The receipt gains a bounded `routes` list with each decision, its bucket and its reason. Bucket-aware routing of the other reads, resumable pagination cursors and cross-process serialization of in-flight requests remain open in #665.
