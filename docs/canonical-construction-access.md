# Canonical construction exposure

[Managed diagnostic access](protected-diagnostic-access.md) · [Owned variants](owned-development-variants.md)

Controlled `improve` and `watch` can automatically record construction and refinement
exposure in one explicitly selected `HistoryStore`. This connects their normal
proposer/author flow; it does not require a separate variant-generation command.
The controller observes available bytes, not semantic dependence or model reads.
Scientific independence, native/provider identity and qualification remain unverified.

```sh
ahl improve PROJECT --agent responses --inference-settings EXPLICIT_SETTINGS.json \
  --evaluation-store PRIVATE_HISTORY --cgroup-root DELEGATION \
  --image-root PINNED_IMAGE --image-sha256 IMAGE_SHA256 --disk-bytes DISK_CAP
```

The same selector works with `ahl watch ... --once`. Real settings explicitly request
provider use; native tests use fake transport, synthetic keys and fixed Python workers.
The selector cannot enable native agents or the separate deterministic contract-repair
mode. Existing recommendation-only policy, configuration scope, trial ceilings,
request/tool quotas, permission gates and resource limits remain in force.

Readonly controller-generated analysis views have no fixed aggregate file,
directory, byte or metadata admission ceiling. Both preparation roles retain the
complete metadata summary; the canonical path copies and pins the same full view
before consumption and rechecks it afterward. A controller-only immutable input
mapping selects this admission policy for the readonly fixture mount. A JSON label
or worker output cannot select it, change mount permissions or supply authority.

Writable worker state keeps its existing 100-file/directory, 1 MiB content and
64 KiB metadata bounds; authored output normalization retains its separate bound.
Harness inputs and other consumers retain their existing defaults. Deadlines,
request/tool/output quotas, memory, processes and scratch-volume limits still
govern execution. Large analysis admission does not promise unlimited physical
resources or unbounded model context. Snapshots retain admitted bytes in controller
memory, without truncation or invented completeness.

## Store and role boundaries

Select the store explicitly. It must be canonical, private and outside the project,
output, methodological skills, selected bank, capture source, runtime image, settings
and credential inputs. Validation occurs before evidence collection, harness copying
or provider dispatch. The controller does not infer a store from a global directory,
another run, a task label or a JSON receipt.

Role inputs and working trees live outside the selected store. Only the baseline,
sanitized metadata/methodology, the proposal seed and explicitly supplied refinement
feedback are made available through existing role mounts and `WorkingState`.
Store control files, snapshots, settings and bindings are host-only. The evaluator
author still receives no candidate or earlier task/oracle view.

Each role gets a process-owned, one-use handoff. The controller binds the actual
input trees and modes, proposal seed, settings, resource selection, configuration
and full evaluator/Python engine. It rechecks them and its issuer PID before
registration and external publication. The actual role also pins its output before
returning, so a later artifact rewrite cannot be repinned as that role's output.
Asset capture must match both identities and full input-tree metadata from that
immutable snapshot, including changes restored before a later read. Only the
controller's manifest rewrite is allowed; publication uses the retained snapshot.
Forked continuations cannot complete a stage, release the parent's project lock or
overwrite its watch completion. A copied object or serialized receipt is not custody.

## Scientific inputs and refinement

An initial stage has **unknown scientific parentage**. Shared baseline instructions,
methodology and runtime settings are control pins; they do not merge scientific
roots. No invented sealed run is used to fill the initial-parent gap.

An accepted author publication records actual prompt, fixture and oracle content
identities before the output reaches its requested destination. These are observed
construction assets, even if the author called a task `heldout`. Legacy split and
grading behavior remain descriptive; the label cannot supply untouched certification.
Known constructed assets cannot obtain fresh managed diagnostic access in that store
through renaming, relabeling, removing a marker or revising the comparison plan.
Ordinary development comparisons remain available.

Before refining, the controller maps its supplied task-status feedback to the same
workflow's actual completed author output. The selected scientific assets become
the next proposer's conservative may-derived parents. Unknown or forged parent
references reject; a raw feedback file cannot mint an owned source. Status text is
observed feedback, not a newly verified task outcome. Candidate-tree output is bound
separately and is not automatically an executable task or an independent root.

`workflow.json` includes private `construction_access` stage IDs, roles and digests.
`complete` means the construction transaction finished; it says nothing about grader
validity, task success, harness benefit, model behavior or adoption. The existing
runner and grader controls continue to decide their own descriptive outcomes.

## Durability and failure

The existing CertificationLedger lock owns schema-4 `constructions`. Prior schema-2
admissions and schema-3 derivations retain their fields; frozen histories are not
rewritten. The standalone schema-1 API remains descriptive and cannot become an
owned invocation. This adds no second ledger, journal, writer, runner or monitor.

Actual input pinning is bounded controller preflight. A stage is pending before
its role copies, seed preparation or first provider request. Pending and unresolved
work blocks managed freshness while unpublished children are unknown. Terminal
space is reserved under the existing 1 MiB ledger ceiling before preparation;
unrelated observations cannot spend it. These are storage bounds, not sample quotas.

One existing parent deadline includes selected-store preflight, copying, roles,
registration, publication and final readback. Watch carries its attempt budget
through this preflight. Its cache identity pins the selector/profile and stable
store-directory identity, not growing ledger contents: the watch's own appends do
not request another model run. Changed store identity or configuration invalidates
the cached invocation rather than upgrading it to current authority.

Interruption, stale input/settings/engine bindings or invalid output never refunds
exposure. Pending/unresolved construction requires intervention; there is no
automatic reset or inferred recovery. Ordinary diagnostic admissions can still run.
If registration completed before publication/deadline failure, private construction
can remain complete without an external-export success claim.

## Remaining scope and native checks

Without `--evaluation-store`, the legacy workflow remains explicitly unmanaged and
unqualified. Raw `construction.author` without an owned handoff remains outside this
association; its [original intentional RED](owned-development-variants.md#remaining-scope-and-executable-evidence)
is retained. Cross-store copies, arbitrary host access, manual semantic rewrites,
scripted-reply delivery and other unobserved artifact flows remain unknown. This
does not establish complete transient-read/write or external-delivery coverage.
Genuine curation/oracle/untouched-lineage authority and full issue #8 remain open.

The [fixed repeated-bank workflow](repeated-improvement.md) shares this explicitly
selected store and construction scope. Its request pins, shared trial limits and
unverified scientific qualification remain in force.

Run `task test:evaluation:construction-access`. Its canonical installed selector
forwards `PYTHON`, `LAYOUT_DIR` and `EXPECTED_PACKAGE_ROOT` and asserts the actual
application import root. Public synthetic controls exercise the normal CLI,
refinement, managed denial, ordinary comparisons, live lock/fork boundaries, stale
pins, deadlines, interruptions, capacity, legacy records and private export markers.
Source controls use cooperative attestations. The optional
`task test:sandbox:kernel:construction-access` composes the same normal workflow
with actual pinned kernel workers, artifact graders and fake transport in the
existing disposable delegated scope. It does not qualify native agents, model
behavior, complete containment or independent scientific roots.
